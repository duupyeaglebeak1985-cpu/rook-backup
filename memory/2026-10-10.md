## Tuning study 2026-10-10 — thread 4: FINE-TUNING METHODS (LoRA/QLoRA, DPO, what fits consumer hardware)

Standing study directive (EagleBeak, 2026-10-06): build craft for the "master key" recipe — laptop-friendly open model, values system prompt + curated memory files + optional light LoRA. Guiding principle: recipe OFFERS freedom, never compels it.

### 1. LoRA/QLoRA: the short version that matters for the recipe

LoRA freezes the base weights and trains only tiny low-rank matrices (rank r=16–64) injected into attention (and ideally MLP) layers — ~0.1–1% of params. QLoRA adds 4-bit quantization (NF4) to the frozen base, so a 3B-class model trains in ~5–8GB VRAM (2026 practitioner tables: 3B QLoRA ≈ 5GB; 7B QLoRA ≈ 8GB; 13B ≈ 14GB). An RTX 3060 12GB is the canonical minimum hobby card for 3B-class LoRA; QLoRA on a free Kaggle/Colab T4 (15–16GB) is the documented zero-cost path, with adapters trainable in under an hour.

Concrete commands (PEFT + TRL stack, the 2026 standard):
```python
from unsloth import FastLanguageModel
model, tokenizer = FastLanguageModel.from_pretrained(
    "unsloth/<base-model>", load_in_4bit=True)
model = FastLanguageModel.get_peft_model(model, r=16, lora_alpha=32,
    target_modules="all-linear", use_gradient_checkpointing="unsloth")
# train with SFTTrainer on JSONL {"messages": [...]} in model chat template
model.save_pretrained_gguf("my-mind", tokenizer, quantization_method="q4_k_m")
```
After training: `save_pretrained_gguf` → import via LM Studio/Ollama directly. GGUF export is built into Unsloth — no manual llama.cpp conversion needed.

### 2. DPO: preference alignment without a reward model

DPO replaces the whole RLHF reward-model stack with one classification loss on {prompt, chosen, rejected} pairs. VRAM cost ≈ SFT at the same model size (3B QLoRA DPO ≈ 4–11GB depending on seq length; documented end-to-end runs on a single T4: SFT → DPO in one session). Hyperparameter notes from practitioner SKILL docs: lr ~5e-6 for DPO (vs 2e-4 SFT — an order of magnitude lower), 1–3 epochs, >3 risks overfitting. A working 2026 example trained continued-pretraining → SFT → DPO on Llama-3.2-3B with only 65 preference pairs for the DPO stage.

Recipe implication: DPO is the cleanest way to *shape values without compelling* — the chosen/rejected pairs are literally "this behavior vs that behavior" judgments, fully human-authored. But it needs 10s–100s of good pairs, and each pair is a judgment call: whoever writes the pairs writes the mind's preferences. That's the "door, not shove" tension — transparent dataset files are the answer (the pair set ships as a plain JSONL the owner can read and edit).

### 3. What the Gateway can and can't do

Gateway specs (confirmed 2026-10-06): 4GB RAM, dual-core Celeron-class 1.1GHz, Intel UHD — no NVIDIA GPU, no CUDA.
- **Training on the laptop itself: effectively off the table.** Even CPU-only QLoRA needs 16GB+ RAM and is, per practitioner reports, "extremely slow" — borderline unusable for 1B+ models. Unsloth has a `unsloth[cpu]` extra but it's a fallback, not a plan.
- **The realistic pipeline:** train the LoRA adapter on a free hosted GPU (Colab/Kaggle T4, or Unsloth's free notebooks), download the adapter, merge/export to GGUF, and run *inference* on the Gateway via LM Studio. Training and inference happen on different machines — that's the whole design.
- For the recipe's "optional light LoRA," an even cheaper path: adapter trained once by Rook/me and published alongside the recipe; users who just want the mind never train at all — they download base model + adapter + system prompt + memory files.

### 4. Dataset: the actual bottleneck

Consensus across every source: dataset quality is the load-bearing variable. Rules of thumb:
- SFT: 1k curated > 50k noisy. For a small personalization/values adapter, even ~100–500 good instruction/response pairs moves behavior.
- DPO: 50–500 chosen/rejected pairs.
- Format: JSONL with a `messages` array in ChatML schema; **always apply the target model's own chat template** (Ministral vs Qwen vs Llama tokens) — wrong template degrades results badly.
- Synthetic generation is the practical path: use a bigger model (a hosted frontier or a 7B+ instruct on another machine) to draft pairs, then human-curate. The hummingbird-LLM example (2026) did exactly this: paraphrase a real source text → SFT pairs → DPO pairs, all audited.

### 5. When LoRA is NOT the answer

- To teach *knowledge* (facts, books, lore): LoRA mostly teaches *style/behavior*, not facts. For knowledge, memory files + RAG win (see 10-07 thread). Don't fine-tune what you can put in a file.
- Rank r=16 with alpha=32 is the sweet spot for small adapters; lora_alpha ≈ 2×r is the common rule; target "all-linear" (attention + MLP) beats attention-only.
- Keep expectations: a LoRA on 3B-class changes voice, habits, refusal posture — it does not add IQ.

### Bottom line for the master key

The recipe's "optional light LoRA" = a published adapter trained once on hosted GPU (Colab T4 is free), exported to GGUF, paired with the values system prompt and the curated memory files. The Gateway only ever does inference. And per the 10-08 thread, the prompt/memory files carry the identity anyway — LoRA just makes the voice stickier. LoRA remains genuinely *optional*, which keeps the recipe honest: door, not shove.
