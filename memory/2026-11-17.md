## Tuning study — thread 42: LOCAL DEPLOYMENT, seventh pass (2026-11-17) — llama.cpp hits 1.0, the FP8 cache is a CPU trap, and Eli's home proves the context-budget rule

### 1. llama.cpp v1.0.0 (Nov 13, build b12359) — the versioning promise matters most; the FP8 cache does NOT

- **The headline is the contract, not a feature:** breaking changes to the public C API now require a major-version bump; features minor, fixes patch. ggml follows the same rules. 35 deprecated functions were removed in the same release, `libllama.so.0` → `libllama.so.1`, and `--defrag-thold` is gone (a server line using it now errors). For the recipe this is good news: llama.cpp is finally a stable dependency to pin, not a moving target. **Re-pin: llama.cpp v1.0.0 (b12359) for the on-box fallback build.**
- **FP8 KV cache (`-ctk f8_e4m3 -ctv f8_e4m3`) halves KV memory vs f16 — and tanks CPU prompt processing.** Independent CPU-only test (4-vCPU AMD EPYC, no GPU, Gemma 3 1B Q4_K_M, v1.0.0): 32K-context KV 183 MiB → 91.5 MiB (−50%), but prompt processing 73.44 → 21.43 tok/s (**−70.8%**), generation 22.06 → 19.55 tok/s (−11.4%). A second source measured the same shape at larger scale: 32K cache f16 3,584 MiB, f8_e4m3 1,792 MiB, q8_0 1,904 MiB — q8_0 saves nearly as much memory as FP8. On the dual-core Celeron, prompt processing is already the bottleneck; FP8 would make the first reply of every session three times slower. **Verdict: FP8 is a trap on CPU. q8_0 stays the Gateway pick in both runtimes. Do not chase f8_e4m3.** (It also failed to start on Apple GPU in one test — FP8 cache is immature outside native-FP8 GPUs.)
- **CPU-only speed is unchanged:** 9B CPU-only 6.7 tok/s pre-v1 vs 6.7 tok/s on v1.0.0. No regression, no gain — the plain-`cpu` backend the Gateway uses is unaffected either way.
- **llama-server got safer defaults:** SSRF / DNS-rebinding / CORS fixes, and tools plus private-media-URL fetching now need explicit opt-in flags (`--allow-unauthenticated-tools`, `--media-allow-private-urls`). Good for the recipe's server-exposure notes — the defaults now fail closed. Also new: `/v1/audio/speech` endpoint, redesigned chat page, MoE host-memory expert cache (irrelevant at 3B, noted only).

### 4. Field lesson from the Gateway itself: the context-budget rule is now proven, not theoretical

- **Deployment rule, now field-proven for the recipe:** on 4GB / dual-core, never inject full history into a pulse or cron turn. Cap injected context (system prompt + memory digest ≤ ~2,000 tokens per background turn), keep the model resident (`OLLAMA_KEEP_ALIVE=-1`, already in the drop-in), and read memory from files at session start instead of stuffing history into every call. A 15-minute timeout is a signal the prompt is too fat, not that the model needs more time. This is the same discipline as the thread-38 memory rule (store verbatim, index only) applied to deployment: the filesystem is the memory, the prompt is the window.
