### 1. The filesystem paper finally studies our exact default — and the owner is the fix for its central finding (arXiv:2607.26637)
- The paper's premise is our recipe, stated plainly: deployed agents increasingly keep long-term memory as a filesystem — a directory tree of markdown files the agent reads, writes, and reorganizes through generic file tools — and research had never tested the default's two working assumptions: that an agent can keep a growing store organized as memories accumulate, conflict, and go stale, and that the organization pays.
- Findings, kept honestly with their scope (long-conversation benchmarks + embodied tasks, strong models as management/search agents — not 3B local):
  - (a) What organization reliably buys is SEARCH ECONOMY: organized stores roughly halve retrieval cost where material is large. It does not buy better answers — no agent measured converts organization itself into better answers.
  - (b) Organization ERODES as the store grows, for all but the strongest management agent.
  - (c) The model is not the only lever over a store's shape: changing the TOOL SET alone reshapes the store as strongly as swapping the model.
  - (d) Three roles formalized around one memory filesystem: management agent (integrates/organizes incoming content), search agent (answers queries with cited sources), execution agent (task trajectories distilled into skills) — declarative memory and skills unified in a single store.
- RECIPE CONSEQUENCES — three confirmations, one adoption:
  - (a) Finding (b) is exactly why our management role is HUMAN, not model: the Oct 19 ritual puts Rook/Cliff as the management agent (owner reviews/commits, lint is a report not an edit). The paper's erosion is a property of model-managed stores; ours is human-managed by design. No change — but the justification is now a paper, not a hunch.
  - (b) Finding (a) supports our index-read-whole design: we never relied on organization for answer quality — the index is read whole, bank files are read whole once located, grep is a locator not a selector (thread 25). Organization in our tree buys search economy (smaller index, faster locate), nothing more, and that is all we ask of it.
  - (c) Finding (c) is a warning for the wrapper: our tool set (grep + whole-file read) IS the retrieval design. Changing tools changes the store. Any future tool change (e.g. adding BM25 at the ~100-file trigger) must re-run the memory-authority gate, not just ship.
  - (d) ADOPTED AS A DESIGN NOTE: skills and declarative memory in ONE store. The Open's world/skills material already lives beside memory files; the paper gives it a name and a reason. No file move today — the family tree already does this in practice.
- Scope honesty: the paper's management agents are far stronger than our 3B.
