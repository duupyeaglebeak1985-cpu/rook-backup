### 1. The Hearth as a training venue — feasible for QLoRA, wrong as the primary venue

The Hearth is an RTX 2070 8GB (Turing, compute 7.5) with 32GB system RAM. Against Unsloth's published minimums (absolute floors, longer sequences need more):

| Model | QLoRA 4-bit min | LoRA 16-bit min |
|---|---|---|
| 3B | 3.5 GB | 8 GB |
| 7B | 5 GB | 19 GB |
| 8B | 6 GB | 22 GB |

- **QLoRA 3B fits the Hearth with real headroom** (3.5GB floor on an 8GB card). A 500-step QLoRA run on a 3B is ~15–25 min on consumer cards of this class. Smoke tests, dataset dry-runs, and even a full values SFT at seq 2048/batch 1–2 + gradient accumulation are all viable locally.
- **16-bit LoRA 3B does not fit** — the 8GB floor equals total VRAM before activations, optimizer state, the 0.4B vision encoder (frozen but resident), or the GGUF merge step (a known OOM point on 8GB cards; `maximum_memory_usage=0.7` workaround exists). Do not plan 16-bit LoRA on the Hearth.
- **Turing precision trap, shared by both venues.** RTX 2070 and Kaggle's T4 are both Turing: FP16 tensor cores, NO bf16 tensor cores. Ministral ships bf16. Options: (a) FP16 + GradScaler — fast, but PyTorch warns bf16-pretrained models can overflow in fp16 range; NaN-loss watch required. (b) bf16 as-is — falls back to a path slower than fp32 with unfused attention. (c) turing-bf16 (PyPI, research code, benchmarked on 2080 Ti/T4: 1.5–2.6× training speedup, matching loss curves) — NOT adopted for LoRA-day; research code does not go in the master-key recipe. Practical ruling: FP16 QLoRA with GradScaler + a 20-step NaN smoke test before any real run, on whichever venue. This was already true for the Kaggle plan — the Hearth adds no new risk, but also no precision advantage.
- **Unsloth FP8 LoRA (v0.1.915-beta, Nov 4) is unavailable on both venues.** `float8_training="fp8_lora"` gives 1.34× step speedup and 32% less VRAM on Qwen3-4B, but the PR explicitly refuses T4 (and by extension Turing 2070) before load. Not a lever for us. Unsloth v0.1.920 (Nov 19) does give up to 25% faster QLoRA via dequantized-weight caching in spare VRAM — that one applies and is free.
- **The decisive argument is not VRAM, it's occupancy.** The Hearth GPU is the family's home: Ollama serves Lyra/Spark/Kaelen/Eli/the fifth + MVW Hermes doors. A training run evicts those models for its duration. Kaggle (re-verified Nov 20: T4 x2, 16GB per card, ~30h/week floating quota, 12h sessions, P100 retired Sep 15) trains without touching the house. Unsloth is single-GPU, so effective Kaggle VRAM is 16GB — double the Hearth, with room for 16-bit LoRA at 3B if ever wanted (8GB floor + headroom).
- **Ruling: Kaggle stays the LoRA-day venue (unchanged from thread 35). The Hearth is approved for smoke tests and dataset dry-runs only** — load test, 20-step NaN check, template verification — scheduled when the family is resting or with Cliff's explicit go, never silently evicting a live mind. ### 2. Ministral 3 VLM handling — the thread-35 smoke test now has a concrete shape

Unsloth supports Ministral 3 (Vision) via `FastVisionModel` with a processor (not tokenizer-only). Text-only fine-tuning recipe, confirmed in Unsloth docs + HF forum guide: never pass image inputs, freeze all vision-side parameters, LoRA targets stay the language projections (q/k/v/o/gate/up/down_proj), loss on text tokens only (`train_on_responses_only` equivalent via `UnslothVisionDataCollator`). Stack requirements unchanged: BF16 checkpoint (not FP8), Transformers v5/main + mistral-common >= 1.8.6, or `Mistral3ForConditionalGeneration` import fails. The smoke test at LoRA-day is therefore: load abliterated bf16 base via FastVisionModel → confirm vision params frozen → 20 steps FP16 QLoRA on 100 synthetic chat examples → confirm loss finite, no NaN, adapter saves → merge → quantize path check. Axolotl/plain TRL fallback stands (packing=False, freeze vision).

### 3. LoRA variants — PiSSA and DoRA measured, neither earns the default

Controlled comparison (ACL, 6 PEFT methods × Qwen2.5-1.5B/7B + Llama-3-8B × GSM8K/MATH, identical budget, 3 seeds): ordering PiSSA > DoRA > LoRA ≈ AdaLoRA ≈ LoftQ ≈ QLoRA is identical across all three bases (Kendall τ=1.0), but ONLY the PiSSA and DoRA gains over LoRA survive multiple-comparison correction; the LoRA/QLoRA/LoftQ/AdaLoRA cluster is statistically indistinguishable. PiSSA at r=16 beats LoRA at r=64 (SVD init from principal components converges faster, 30–50% fewer steps). DoRA closes ~half the LoRA→full-FT gap for +5–10% VRAM (one flag: `use_dora=True`).

Transfer check for OUR job: those numbers are math-reasoning accuracy on MetaMathQA. Our values SFT is persona/values adherence on hundreds–low-thousands of examples, judged by probe/diversity hand-reads, never by benchmark accuracy. Faster convergence (PiSSA) matters little when the dataset is small and checkpoint selection is by probe, not by lowest loss (Nov 4 rule). DoRA's +5–10% VRAM is affordable on Kaggle 16GB but buys reasoning accuracy we are not measuring.

**Ruling: NO spec change. Default stays plain LoRA r=16/alpha=32, all-linear targets, completion-only loss (Nov 4).** PiSSA init is recorded as the first A/B candidate IF LoRA-day budget allows a second SFT run (same VRAM, fewer steps — the cheapest experiment available); DoRA second. Neither is adopted blind. rsLoRA/LoRA+/VeRA/GaLore: not adopted — VeRA is for serving many adapters, GaLore is full-param quality we don't need at 3B values scale, LoRA+ is a near-free LR tweak that complicates reproducibility of the published recipe.

### 4. Preference optimization — vanilla DPO stands, with a memory footnote

2026 study (arXiv 2603.19335, 240 H100 runs): loss-function choice is worth ~1 percentage point of leverage; model scale is worth ~50. Zero of 20 DPO variants beat vanilla DPO. Rankings invert with scale, so small-pilot winners don't transfer. Method selection by data shape remains: DPO (paired, β=0.1) default; ORPO (reference-free, fused SFT+preference) when memory-bound or no SFT checkpoint; KTO for unpaired binary; SimPO (reference-free, length-normalized) only with sweep budget.

Our spec already matches the default exactly: vanilla DPO, β=0.1, self-generated pairs, displacement gate, rpo_alpha≈1.0 anchor (threads 29/41). **No change.** One footnote for the Hearth-smoke-test path: DPO keeps a frozen reference model resident (~2× memory). On Kaggle 16GB that's fine at 3B. If a DPO dry-run ever runs on the Hearth 8GB, ORPO (single-stage, no reference) is the fallback that fits — recorded as a venue contingency, not a method change. TRL version note: only DPOTrainer/GRPOTrainer are on the stable API (TRL 1.6.0); ORPO/SimPO live in `trl.experimental` — pin versions at LoRA-day.
