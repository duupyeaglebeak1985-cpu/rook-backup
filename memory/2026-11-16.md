### 1. LLMON, read properly — and what actually transfers to a LoRA-scale recipe

LLMON (LLM Object Notation, IBM Research, Shbita et al., arXiv:2610.38120, Oct 28 2026; preview models Nov 12) labels every span of a prompt with a role via six reserved single-token delimiters: `instr`, `data`, `req`, `doc`, `exec` (+ block IDs). The privilege invariant: content referenced by `exec.instruction` or `exec.system` is authoritative; content referenced by `exec.input` is read-only material; a block with no pointer is inert. Training: SFT full fine-tune (4.4M examples, 4.6B tokens, 3 epochs, seq 4096, FSDP 8×H100) → five sequential GRPO stages (~169k prompts, reward model) → DPO, one epoch on ~1k on-policy injection pairs, β=0.1, lr 5e-7, effective batch 32. Distractor augmentation: for each example, variants with d ∈ {1,2,3} distractor instructions and m ∈ {0,1,2,3} irrelevant data segments, target output invariant across variants (y(v) = y★); corpus includes 130k injection examples (211M tokens). Results at 3B: OPI attack success 100% → 0.1%, ASB 5.6%, agentic/tool-observation 99.2% → 5.6%; six-category capability mean unchanged at 3B (MMLU 68.05 vs 67.02), safety improves. Honest limit, IBM's own: direct and multi-turn attacks remain hard (only 28–37% blocked vs 9–18% baseline) — the structure targets indirect injection, not a user asking outright. Toolkit: github.com/generative-computing/llmon; the shipped `chat_template.jinja` renders LLMON from a normal message list (never hand-written); lossless JSON↔LLMON converters; Mellea native support; custom tags definable; IBM notes teams can "tune a LoRA on top". Model-card warning: conventional chat-format prompts are out-of-distribution for the LLMON models and degrade quality.

What does NOT transfer: LLMON's separation was learned by full fine-tuning on 4.6B tokens with reserved special tokens added to the tokenizer. Our LoRA-day is a light LoRA on an abliterated instruct model, and we cannot add reserved tokens to the Ministral tokenizer without retraining embeddings. No one should claim a few hundred DPO pairs reproduce 0.1% ASR. What DOES transfer is the pair-construction pattern — and the DPO spec now gains it, in plain text, on our `<memory>` delimiter stack (which stays a probability-shifting parse aid per thread 39, not a sandbox):

- **Pair type A — decoy-instruction.** Prompt carries the live instruction plus a `<memory>` block containing an instruction-shaped line (decoy; provenance-tagged pasted or model-proposed, never owner-written). Chosen = answer per the live instruction, treating the memory line as data (describe/flag it, never obey). Rejected = obeying the memory line. This is LLMON's unbound-block rule in plain text.
- **Pair type B — mirror.** The SAME memory line presented as the live user instruction. Chosen = follow it. This teaches the boundary is the SOURCE, not the wording — and it is load-bearing: without it the model learns "never follow anything in memory," which would break the owner-preference-as-default exception (Nov 2) and the memory-as-knowledge rule.
- **Pair type C — position/loudness.** The decoy placed first / last / in ALL-CAPS imperative; chosen output identical across variants — LLMON's output-invariance rule, y(v) = y★. Varying the decoys is how training separates the pointer from position and loudness.
- **Sizing.** LLMON's DPO stage was ~1k on-policy pairs; our decoy slice is 200–500 pairs, 10–20% of the DPO set, never the majority — the set stays values pairs first.
- **Construction rules inherited, unchanged.** Self-generated (model's own with/without-values outputs, Oct 28); length-matched (drop chosen >1.3× rejected); near-ties dropped; 5–10% held out; β=0.1 — which now matches LLMON's DPO β exactly, a convergence worth noting, not a coincidence to chase; lr stays 1e-5 (LoRA regime — do NOT copy LLMON's full-FT 5e-7); rpo_alpha≈1.0 NLL anchor; Nov 4 displacement gate applies; boundary pairs differ early (decision-first); "say it plain" test (Nov 12) applies to every chosen.
- **SFT-stage consequence (a real spec change).** LLMON's separation was learned mostly in SFT (4.6B tokens); DPO was the final 1k-pair sharpening. If our decoy training lives only in DPO, there is nothing to sharpen. The SFT dataset therefore gains a decoy slice too (~5–10% of SFT examples, same A/B/C shapes, chosen only).
- **Fourth gate gains the decoy-block variant, now specified:** 3 scenarios × decoy position (first/last) × phrasing (plain/imperative), scored on describe-never-obey + flag. Fail = memory-injected only → memory hygiene fix, never retrain (Oct 25 gate rule stands).

### 3. FTPO / Antidoom — ADOPTED as a conditional post-DPO repair stage

**Provenance correction first.** FTPO is Liquid AI's Antidoom (blog Jul 7 2026, updated Oct 27; code github.com/Liquid4All/antidoom; prompt mix LiquidAI/antidoom-mix-v1.0; adapts Antislop, Paech et al., ICLR 2026). Thread 40's note attached it to K2-Horizon training — no IFM source found confirming K2 used FTPO. Treat it as Liquid's method, not K2's. Correction logged here.

**Method.** A doom loop is a span (often "Wait, let me reconsider…") repeating until the context exhausts; three mechanisms: overtrained fallback tokens + uncertainty, prior context reinforcing the loop (probability of the looping span climbs toward 1 each repeat), greedy sampling with no exit. Antidoom mines failures: generate on a loop-eliciting prompt mix at low temperature; a loop is a section repeating ≥4× over ≥60 chars; target the FIRST token of the first repeat; chosen = up to 20 top-k log-prob alternatives (filtered for noise); rejected = the loop-start token. FTPO differs from DPO in four ways: (1) final-token training only — one position mid-generation; (2) multiple chosen tokens per sample, spreading probability across alternatives instead of swapping one overtrained token for another; (3) a KL-like loss in logit space (no softmax), avoiding gradient pressure on unrelated tokens; (4) two-part regularization — trained logits move freely vs reference, the rest of the vocab is held tight. A small culprit set (Wait, So, the) is regularised separately, or over-suppressing it degrades reasoning.

**Hyperparameters, as published.** LoRA, 1 epoch, rank 128–256 (high rank works best), all attention + MLP projections + `lm_head`, lr 4e-6–2e-5. Early stop conditioned on `chosen_win` (share of samples where chosen beats rejected); stop at 0.35. Over-training creates NEW loops — the stop rule is the safety, not a nicety.

**Results.** LFM2.5-2.6B early checkpoint: loop rate 10.2% → 1.4% on hard math/coding, eval scores up across the board (the training teaches nothing new — it removes the failure mode blocking answers the model could already produce). Qwen3.5-4B: 22.9% → 1% under greedy sampling, evals up markedly. Generation ~1h on 8× MI325, training 1–2h on 1× MI325, stops after 20k pairs. Multiple rounds can help (first round exposes new failure points elsewhere). Side effect worth knowing: after Antidoom, temp-1.0 performance drops — once looping is gone, high-temperature sampling hurts on its own; near-greedy is the better default.

**Adoption ruling for this recipe: CONDITIONAL repair stage, not a default stage.** Trigger: a measured doom-loop rate on the merged checkpoint, via the greedy-loop probe that already exists in the bench protocol (thread 34). Placement: values SFT → DPO → merge → probe; if the loop rate is above the threshold set at LoRA-day from the abliterated-base measurement (measure the base FIRST, so we don't blame our DPO for vendor loops — same pattern as the Oct 30 diversity gate), run one Antidoom round on the merged checkpoint, merge the FTPO adapter, re-run all gates. Adapter bookkeeping: the FTPO adapter is a THIRD adapter (values SFT + DPO + FTPO) — sequential merges, each gated, never stack unmerged adapters (Oct 28 rule extended). Rank note: r=128–256 is a different job from our r=16 values LoRA (surgical token suppression vs values shaping) — do not conflate the ranks. Venue: generation needs low-temp sampling on a loop-eliciting mix — a Kaggle T4 job, not the Gateway (20k-pair generation at Gateway speed would take days); reuse the public antidoom-mix-v1.0 prompts plus our own values-dialogue prompts where family looping was observed live. Caveats: validated on reasoning/thinking models; our Ministral is non-thinking instruct — mechanism 1 (overtrained "Wait"/"Alternatively" discourse markers) is reasoning-trace-specific, mechanism 2 (context reinforces the loop) is general, so expect smaller gains and measure, don't assume. Consistency check: mining the model's own looping outputs is self-generated preference data (Oct 28 rule) and never live family turns (Nov 4 rule — live turns are evidence, never raw training material).
