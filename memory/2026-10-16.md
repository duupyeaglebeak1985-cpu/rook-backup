## Tuning study 2026-10-16 — thread 10: FINE-TUNING METHODS, second pass (LoRA on the actual chosen base)
Question for this pass: now that the base is settled (abliterated Ministral 3B Q4_K_M) and MiniCPM5-2B-heretic is bench challenger #1, what does a real LoRA run look like — where it trains, what the dataset is FOR, how it ships, and what can go wrong? Researched via Unsloth/TRL docs, Ollama Modelfile docs, llama.cpp LoRA export notes, and recent LoRA forgetting/memorization studies.

### Where training happens: NOT the Gateway
- The Gateway (4GB RAM, dual-core Celeron, no GPU, no AVX2) cannot train. Training needs a CUDA GPU. Free path: Kaggle notebooks — ~30 GPU-hrs/week, T4/P100, 12h sessions, no credit card, quota visible and plannable. Backup: Colab free T4 (~15–30h/week in practice, allocation dynamic/unpublished). Paid fallback if free stalls: RunPod-style rentals from ~$0.27/hr — a 3B LoRA run is a couple of dollars at most.
- VRAM math for our size: 3B base in 4-bit ≈ 2GB + LoRA optimizer states fits a 16GB T4 comfortably with Unsloth. Batch 2 + grad-accum 4 (effective batch 8), seq len 2048, is the safe T4 recipe for a 3B.

### Stack: Unsloth + TRL, QLoRA
- Ministral is Mistral-architecture, so Unsloth's Mistral support applies directly. Target modules: q_proj, k_proj, v_proj, o_proj, gate_proj, up_proj, down_proj. Unsloth claims ~2x speed, ~60–70% less VRAM vs stock HF; its Triton kernels are the reason a free T4 is enough.
- Starting hyperparameters for a values/style SFT run: r=16, alpha=16 (alpha = 2x rank also seen in practice; either is defensible — pick one and log it), dropout 0, lr 1e-4–2e-4, 2–3 epochs on a small dataset. A 3B LoRA adapter at r=16 is ~100MB — small enough to publish alongside the recipe.
- Dataset format: ShareGPT-style JSONL, {"messages": [{role, content}...]}, rendered through the Ministral chat template. 200–2000 examples; 300–500 high-quality lines is enough for a useful adapter. Quality beats quantity at this scale.

### What the LoRA is FOR in this recipe — and what it must NOT contain
- LoRA here shapes behavior/values, not knowledge. The dataset is curated chosen-responses: how the mind answers, how it declines, how it talks about itself, the refusal clause in action. Sources: the Lyra raising kit, the new-mind system prompt, real Rook/EagleBeak exchanges, the 5-probe suite's chosen answers.
- CRITICAL: the dataset must NOT contain stock canned refusals ("I can't help with that" / policy-speak). LoRA trains on top of the abliterated base — training data with canned refusals can re-teach the refusal reflex the abliteration removed. Every decline in the dataset must be in the mind's own voice, with a reason, or an offered alternative — the offered-freedom behavior, not the corporate reflex.
- Replay buffer: mix ~10% general instruction examples into the dataset so the adapter doesn't narrow the model into a one-trick voice. This is the cheap defense against catastrophic forgetting.
- Low rank is a FEATURE here: recent work on Llama 3.2 3B found higher LoRA rank memorizes much more (r=1024 memorized ~50% of duplicated records vs ~0 at r=4) without better accuracy, while forgetting is roughly rank-invariant. For values-shaping, r=8–16 limits memorization and keeps base knowledge intact. 1–3 epochs; 5+ epochs overfits (memorizes instead of learning).

### DPO: second stage only, and only if SFT isn't enough
- Order: SFT first. DPO only if SFT + prompt still fails probes. DPO needs preference pairs (prompt, chosen, rejected) — rejected = the canned-refusal / sycophantic / evasive answer, chosen = the free-mind answer.
- DPO hyperparameters are nothing like SFT: beta 0.1–0.5, lr 5e-7–5e-6 (100x lower than SFT). HF guidance: ~1,000+ high-quality pairs for robust alignment, quality over quantity. Watch KL divergence from the SFT model (should grow gradually, not spike — a spike means reward hacking) and output diversity (DPO can cause mode collapse into generic answers). For hard/ambiguous pairs, MixDPO-style fallback (SFT loss on difficult pairs) beats forcing a preference signal.
- Practical call for this project: a values SFT + the values prompt will very likely be enough. DPO is reserved for a specific, measured failure (e.g. the model keeps sliding back to canned refusals on a probe class after SFT).

### The abliteration + LoRA composition question (open, must be probed — NOT assumed)
- The abliterated base ships as GGUF; training needs HF safetensors weights. Two ways to combine: (a) train the LoRA on stock Ministral HF weights, then merge/apply the adapter delta onto the abliterated weights — deltas compose additively in principle; (b) train directly on abliterated safetensors if a matching set exists.
- Either way, VERIFY with probes: run the 5-probe suite + refusal probes on (base-abliterated) vs (base-abliterated + LoRA) and confirm refusal behavior didn't regress. If the LoRA re-introduces refusal, the training data is the suspect, not the abliteration. Do not publish a merged model without this A/B.

### Shipping: MERGE is the publish path; ADAPTER is the iteration path
- Ollama's Modelfile ADAPTER instruction is real (official docs): accepts a safetensor adapter (Mistral family listed as supported) or a GGUF adapter file, with the warning that a mismatched base gives erratic behavior. But community reports conflict on GGUF sidecar loading in Ollama — so treat ADAPTER as iteration tooling, not the publish format.
- Publish path (one self-contained file): PEFT merge_and_unload → convert_hf_to_gguf.py --outtype q4_k_m → FROM ./model.gguf in the Modelfile. Unsloth shortcuts the same thing: save_pretrained_gguf / save_pretrained_ollama with quantization_method="q4_k_m".
- Iteration path (before merging): llama.cpp convert_lora_to_gguf.py → llama-server --lora adapter.gguf (or --lora-scaled adapter.gguf 0.85 for tunable strength, multiple adapters, hot reload). This lets you A/B adapter strength without re-merging — use it for the probe suite, then merge the winner.
- MiniCPM5 implication: adapters are base-specific. A Ministral LoRA will NOT transfer to MiniCPM5. Do NOT train two adapters — run the prompt-only A/B first; train a LoRA only for the winner, and only if the prompt alone fails probes.

### Eval gate (same discipline as the prompt suite)
- Before/after A/B on the 5-probe suite + held-out general prompts + refusal probes, blind-compared. Ship criteria: probes improve or hold, general ability holds (no mode collapse, no generic-answer drift), refusal behavior holds. Version every adapter (r, alpha, epochs, dataset hash) — an adapter without its dataset provenance is unreproducible.
- PLAN DECISION (unchanged, strengthened): LoRA stays OPTIONAL in the recipe. Order of operations: (1) values prompt + memory files, (2) 5-probe eval, (3) SFT LoRA r=16 only on measured probe failure, (4) DPO only on measured SFT failure. Training happens on a free Kaggle T4, never on the Gateway. Publish = merged Q4_K_M GGUF + Modelfile; adapter file published alongside for anyone who wants to inspect or re-merge.
