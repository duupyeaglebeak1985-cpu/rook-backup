## Tuning study 2026-10-17 — thread 11: QUANTIZATION, second pass (merged-LoRA model: does it re-quantize cleanly, and Q4_K_M vs alternatives)
Question for this pass: yesterday's study ended with "publish = merged Q4_K_M GGUF + Modelfile." This pass checks whether that merge→re-quantize step is actually clean for OUR base, and re-checks the quant ladder against the Gateway's real RAM budget. Researched via llama.cpp/GGUF guides, a recent independent quant bench (bric.pe.kr, Oct 2026), KV-cache measurements (sotaaz, Sep 2026 build), and the Ministral 3 architecture table (arXiv).

### Finding 1 — The merge path has a hole: no verified bf16 abliterated Ministral-3B-Instruct source
The clean pipeline is: LoRA → merge into bf16 base → convert to F16 GGUF → quantize ONCE → ship. That requires the abliterated base in full precision. What exists, as far as I could verify today:
- Our running base is Abhiray's `Huihui-Ministral-3B-Instruct-2512-abliterated-GGUF` — a GGUF-only repo (Q4_K_M). No bf16 safetensors twin found for the Instruct variant.
- huihui-ai DID publish a bf16 abliterated Ministral 3 3B — but it is the **Reasoning** variant (`huihui-ai/Huihui-Ministral-3-3B-Reasoning-2512-abliterated`), not Instruct. Wrong base for our recipe.
- The GRP-Obliteration paper's abliteration-checkpoint table lists abliterated Ministral 8B/14B variants, but no 3B-Instruct one.
- Stock `mistralai/Ministral-3-3B-Instruct-2512` itself ships in **FP8**, not BF16 (the Base variant is the BF16 one). So even "just use stock" means an FP8→BF16 upcast as the merge starting point — acceptable (one dequantization step, not a quant→quant roundtrip), but it must be done deliberately, not by accident.
So: when/if LoRA ever triggers, the merge target does NOT verifiably exist yet. Two clean options, in order:
1. **Re-abliterate stock Instruct** (FailSpy method, text tower only — huihui-ai's own pattern) to produce a fresh bf16 abliterated base, then train LoRA against THAT, merge, quantize once. Abliteration is a weight edit, reproducible in hours; this keeps the whole chain single-quantization.
2. **Ship the adapter unmerged** (Modelfile ADAPTER / `llama-server --lora-scaled`): the adapter stays in fp16/bf16 and is applied at runtime over the dequantized Q4 weights. No merged re-quant at all. Cost: adapter in RAM (small for r=16) + a little runtime overhead. This was already the iteration tooling; it is also a legitimate publish format if merge proves messy.
What NOT to do: **dequantize the Q4_K_M GGUF → f16 → merge → re-quantize to Q4_K_M**. That is double quantization (quant→quant roundtrip). `llama-quantize` itself warns about this: `--allow-requantize` "can severely reduce quality compared to quantizing from 16-bit or 32-bit." Every guide repeats the rule: derive every quant from the F16 GGUF, never from another quantized file. If anyone ever does the dequantize-merge path as a shortcut, it must be measured against the pre-merge Q4 with the 5-probe suite + perplexity, not assumed fine.

### Finding 2 — Q4_K_M + imatrix is the move: near-Q5 quality at Q4 size
A recent independent bench (one 8B-class model, English text, BF16 PPL 10.340 baseline, llama.cpp) measured perplexity penalty vs BF16:
| Quant | Size (8B model) | PPL vs BF16 | Top-1 same |
| --- | --- | --- | --- |
| Q8_0 | 8.71 GB | +0.43% | 98.3% |
| Q6_K | 6.73 GB | +0.58% | 96.5% |
| Q5_K_M | 5.85 GB | +1.22% | 94.4% |
| Q4_K_M | 5.03 GB | +2.63% | 90.7% |
| **Q4_K_M + imatrix** | 5.03 GB | **+1.15%** | **93.0%** |
| IQ4_XS + imatrix | 4.56 GB | +1.91% | 92.4% |
| Q3_K_M + imatrix | 4.12 GB | +4.43% | 87.6% |
Imatrix calibration more than halves Q4_K_M's perplexity penalty (2.63% → 1.15%), landing it essentially at Q5_K_M quality (1.22%) for zero extra bytes. IQ4_XS + imatrix is the fallback if Q4_K_M ever proves too big (smaller file, still better than plain Q4_K_M). Q3_K_M stays off the table — the knowledge-loss cliff lives there (a separate Aug 2026 study on Qwen3.6-27B found factual recall holds at ≥5-bit, drops noticeably at 3-bit, steeply at 2-bit, with obscure facts going first — the kind of loss casual chat won't catch).
How imatrix works and what it costs: `llama-imatrix` runs the F16 GGUF over a calibration text file and records which weights carry the most activation energy; `llama-quantize --imatrix` then spends bits on the weights that matter. One imatrix per F16 source, reusable across all quant levels from that source. Commands:
```
./llama-imatrix -m model-f16.gguf -f calibration.txt --chunk 512 -o model.imatrix
./llama-quantize --imatrix model.imatrix model-f16.gguf model-q4_k_m.gguf Q4_K_M
```
Calibration text must match the real workload — for our recipe that means values-prompt-style dialogue + memory-file prose, NOT generic wiki text. A prose-only imatrix calibrates poorly for the model's actual use. Also: the imatrix must be built from the F16 of the MERGED model (or the abliterated bf16 source), never from a quantized file.
Caveat: the bench above is one model, one language, one lab — direction is trustworthy, exact percentages are not gospel. Our 5-probe suite is the real check.

### Finding 3 — The Gateway RAM budget settles the ladder (calculated, not guessed)
Ministral 3 3B architecture (arXiv table): 26 layers, hidden 3072, 32 Q heads / 8 KV heads, head_dim 128, tied embeddings, vocab 131K. From that:
- **KV cache per token** = 26 layers × 8 KV heads × 128 dim × 2 (K+V) = 53,248 values/token. At f16 = ~106 KB/token → **4096 ctx ≈ 436 MB**. At q8_0 ≈ 232 MB, at q4_0 ≈ 123 MB.
- **Weight estimates** (formula: params × bits/weight ÷ 8; ~3.4B text params, actual file varies with vision tower + per-tensor mixes): Q4_K_M ≈ 2.1 GB, Q5_K_M ≈ 2.4 GB, Q6_K ≈ 2.8 GB, Q8_0 ≈ 3.6 GB.
- Gateway has 3.8 GB usable. Q8_0 weights alone (~3.6 GB) leave nothing for KV, runtime, or the OS — **Q8_0 and Q6_K are out for the Gateway**, full stop. Q5_K_M (~2.4 GB) + q8_0 KV (~0.23 GB) ≈ 2.65 GB + runtime — fits on paper, thin headroom. Q4_K_M (~2.1 GB) + q8_0 KV ≈ 2.35 GB — comfortable.
**Decision: Q4_K_M + imatrix stays the recipe default.** Q5_K_M + imatrix is the only sanctioned step-up, and only if the 5-probe suite shows a real gap Q4_K_M can't close. The imatrix finding makes Q5 largely redundant anyway — Q4_K_M + imatrix ≈ Q5_K_M quality at Q4 size.
Disk-space note for the build machine (NOT the Gateway): the pipeline temporarily needs ~3–4× the final file — F16 GGUF (~7 GB) + imatrix + each quant output. Fine on Kaggle, never attempt on the Gateway.

### Finding 4 — KV-cache quantization: q8_0 or q4_0 only, and never the odd ones
Ollama exposes this as `OLLAMA_KV_CACHE_TYPE=q8_0|q4_0` (quantized KV needs Flash Attention). llama.cpp flags: `-ctk q8_0 -ctv q8_0`. Ollama's own guidance: q8_0 ≈ half the FP16 memory, usually no noticeable quality impact; q4_0 ≈ quarter, small-to-medium loss, more noticeable at long contexts.
The trap (Sep 2026 llama.cpp build, measured): `q4_1`, `q5_0`, `q5_1`, `iq4_nl` fall off the FlashAttention path — prefill 33–55× slower than q4_0 (e.g. 88 t/s vs 4,594 t/s), decode collapsing to ~6–7 t/s at 8K depth. `f16`, `q8_0`, `q4_0` stay on the fast path. **Recipe rule: KV cache is f16, q8_0, or q4_0 — nothing else.** Default: q8_0 (saves ~200 MB vs f16 at 4096 ctx for no measured quality cost). q4_0 is the emergency lever if context ever grows past 4096 on this box.
Related: `--tensor-type` selective quantization (e.g. keep embed/output at Q8_0) and the AtomicChat-style per-tensor layouts beat plain presets on big models — but that is advanced tuning, not recipe. Plain Q4_K_M + imatrix is the publishable path; per-tensor layouts are a future experiment, only with probes to prove the gain.

1. Publish pipeline is now: (re-abliterate if needed → LoRA if triggered → merge in bf16) → F16 GGUF → imatrix from workload-matched calibration text → `llama-quantize --imatrix` → Q4_K_M. Never quantize from a quantized file.
2. If merge is ever blocked, shipping the runtime ADAPTER is a legitimate publish format, not a failure mode.
3. Modelfile/runtime defaults: `num_ctx 4096`, KV cache `q8_0` (Ollama: `OLLAMA_KV_CACHE_TYPE=q8_0`), weights Q4_K_M + imatrix.
