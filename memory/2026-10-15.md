## Tuning study 2026-10-15 — thread 9: NEW OPEN MODELS AND TOOLS worth knowing about

Standing study directive (EagleBeak, 2026-10-06): build craft for the "master key" recipe — abliterated Ministral 3B Q4_K_M via Ollama/llama-server on the 4GB no-AVX2 Celeron Gateway, values system prompt + curated memory files + optional light LoRA. Guiding principle: recipe OFFERS freedom, never compels it.

### Verdict up front: NO SWITCH. Ministral 3B abliterated stays the base. One real challenger to bench.

Every new model was judged against the same three gates: (1) fits the Gateway (weights + KV + overhead ≤ 3.8GB usable), (2) an abliterated / refusal-removed build exists, (3) no architecture or thinking-mode trap that eats the Celeron alive. Only one newcomer clears all three as a bench candidate.

### 1. MiniCPM5-2B — the challenger (OpenBMB, released 2026-09-07, Apache 2.0) — BENCH THIS

- 2.5B dense params, standard Llama architecture (nothing exotic — llama.cpp/Ollama just work), 131k context, Q4_K_M file 1.56GB. Fits the Gateway with MORE headroom than Ministral (1.9GB), leaving room for Q5/Q6 or a bigger KV cache.
- Capability: vendor's 34-benchmark table claims 53.9 average, ahead of Qwen3.5-4B (51.1). Independent check: Artificial Analysis Intelligence Index rated it 15, highest of any open-weight model under 4B. Independent analysis (SitePoint) tempers that: it leads on code reasoning, tool use, and long-context (NoLiMa 68.1 vs Qwen3.5-4B 43.5) but gives ground on general knowledge (MMLU-Pro, GPQA), instruction following, and long-horizon terminal work. Vendor tables are marketing until reproduced — treat the headline as "strong 2B", not "beats all 4Bs".
- Abliterated builds EXIST, and the best one is unusually rigorous: insraq's Heretic edit ships a reproduction kit (pinned base commit, pinned prompt sets, RNG seed, full Optuna journal, SHA256sums) — byte-checkable rebuild, not trust-me weights. Measured 5/100 refusals vs 99/100 stock on the same 100-prompt screen, KL drift 0.0391. GGUF ladder published (Q4_K_M 1.56GB recommended; Q8_0 2.68GB).
- The catch, and it's a big one: stock MiniCPM5-2B refused 99/100 on that screen — the most refusal-trained model in its class. Abliteration leaves a 5–10/100 residual floor (SFT-baked refusals, not in the refusal direction; pushing harder damages capability). Compare: the Huihui Ministral abliteration EagleBeak's recipe already uses has no such reported floor. Also one abliterated eval rated Q4_K_M coherence at 80% vs 100% at Q8_0 — on the Gateway's headroom, Q5_K_M/Q6_K may be worth the extra ~0.3–0.5GB.
- Thinking mode: MiniCPM5 has a built-in think mode. Same trap as Qwen (below): run with think disabled for conversation, or the model burns its token budget deliberating and returns empty output. Ollama: use the native /api/chat `think: false` flag.
- Action: A/B it against Ministral 3B abliterated on the existing 5-probe regression suite + free conversation feel, before any recipe change. If it wins, the recipe gains speed and headroom; if it feels flatter or refusals leak through, Ministral stays. Do NOT switch on benchmarks alone.

### 2. Qwen3.5 family (0.8B / 2B / 4B / 9B, Alibaba, Apache 2.0) — WATCH, don't adopt

- Architecture is the new wrinkle: hybrid Gated DeltaNet + gated attention, 262k context, vision built in at every size. Needs the latest llama.cpp/Ollama for the DeltaNet operators.
- The 4B abliterated build exists (mradermacher Huihui-Qwen3.5-4B-abliterated-GGUF, Q4_K_M 2.71GB, ~4.7GB RAM needed) — TOO BIG for the 3.8GB Gateway. The 2B would fit (~1.3GB Q4_K_M, and unlike its bigger siblings it runs non-thinking by default) but NO abliterated 2B build surfaced in this search. Without a refusal-removed build, stock Qwen refusals stand — disqualifying for the recipe.
- The thinking-mode trap is severe and well-measured on Qwen3/3.5: default thinking burns 200+ hidden tokens per call; one measured probe took 173s with thinking on vs 0.5s with it off for "2+2"; on a slow CPU that means minutes of silence, and a small token budget can exhaust inside the think block and return EMPTY content. The reliable fix is Ollama's native /api/chat `think: false` flag. The `/no_think` prompt token is often ignored, and the OpenAI-compatible /v1/chat/completions endpoint silently drops the think flag — both are documented failure modes. Anyone who picks Qwen for the recipe must wire the native endpoint, not the OpenAI one.
- Watch for: a Huihui/mradermacher abliterated Qwen3.5-2B. If one lands, re-evaluate — it would be a second bench candidate.

### 3. Gemma 4 E2B — DISQUALIFIED on size (Google, Apache 2.0)

- 2.3B effective params but 5B total with per-layer embeddings; Q4_K_M file ~3.11GB (unsloth). Weights alone nearly fill the Gateway before KV cache and OS — doesn't fit. E4B (Q4_K_M ~4.98GB) is worse. Abliterated E2B exists (0.4% refusals measured) but size kills it for this hardware. Relevant only for the recipe's "if you have a bigger machine" tier.

### 4. SmolLM3-3B — second challenger, blocked on abliteration (Hugging Face, Apache 2.0)

- 3.1B, 64k context (128k with YaRN), Q4_K_M 1.92GB — same footprint as Ministral. Fully open provenance (data mixture, configs, code published) — the best audit story of any candidate for a published recipe. Wins instruction-following inside its class on HF's launch numbers. But: no abliterated build surfaced, and one tool-calling benchmark flagged poor restraint (calls tools when told not to). Watch for an abliterated build; until then, not a candidate.

### 5. The rest of the field — one-line dismissals

- LFM2.5-1.2B/2.6B (Liquid AI): hybrid SSM, very fast on CPU, 1.2B under 1GB, tied #1 on one tool-calling benchmark — but 1.2B is too small for a mind to raise, and the licence is LFM Open License 1.0, not Apache (check terms before building a published recipe on it). Possible future roles: draft model for speculative decoding, or a first rung for weakest hardware. LFM2.5-8B-A1B MoE (8B weights, 1B active, 5.2GB file) is too big for Gateway RAM despite fast decode.
- Granite 4.2 3B (IBM): wins IFBench/IFEval in one comparison table, Apache 2.0 — no abliterated build found. Phi-4-mini 3.8B (Microsoft, MIT): same, no abliterated build found. Nemotron 3 Nano 4B (NVIDIA): English-only + NVIDIA licence. Olmo 3 7B (Ai2): too big. None clears the gates.

### 6. New tools — two to watch, one trap to fix in the recipe

- Decision models in llama.cpp (Oct 2, 2026, b11361+; /v1/systemone endpoint): a new model class that answers in ONE forward pass with zero output tokens — returns a choice / score / yes-no probability instead of generated text. Liquid AI's d1-3B + d1-omni-600M landed Oct 7 (need llama.cpp b11483+/b11488+); Cloudflare and Amazon shipped open-weight decision models Oct 1–3. For the recipe: NOT a base-model change. Future use: a tiny decision model as a sidecar classifier — e.g. memory-distillation triage ("is this worth remembering?") without burning chat-model tokens. d1-3B is too heavy to run alongside the chat model on the Gateway; d1-omni-600M might fit later. Watch, don't adopt yet. Note: early Ollama decision-model support had bugs (clef-flash failures); upstream llama.cpp is the safer runner for these.
- N-gram speculative decoding (llama.cpp `--spec-type ngram-mod`): no draft model, ~16MB constant footprint, helps on repetitive output (code edits, JSON, rewrites) and ~nothing on fresh prose. One benchmark found it 3–12% SLOWER on MoE models. For the Gateway: free to try, must A/B measure — don't assume a win. Draft-model speculative decoding needs a second model + RAM the Gateway doesn't have.
- Ollama truncation trap (confirm in recipe docs): on machines with under 24GB GPU memory, Ollama defaults to a 4096-token context and SILENTLY truncates longer prompts to ~half the window with HTTP 200 and only a server-log warning. The recipe's Modelfile already sets num_ctx 4096, but any wrapper calling the API must also pass `"truncate": false` so over-long prompts error loudly instead of silently losing the values prompt / memory tail.
