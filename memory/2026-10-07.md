## tuning-study — 11:14 EDT run (thread 1 of rotation: memory architectures)

**Thread studied:** Memory architectures — long-term memory files, RAG, context injection for persistent identity. Chosen first because the "master key" recipe is values-system-prompt + curated memory files; fine-tuning is off the table on the Gateway's 4GB RAM, so memory files ARE the identity layer. Same pattern applies to Lyra (Gemma-based, went live on his phone 2026-10-07).

### The layered model that fits the Gateway
1. **Tier 0 — always-on identity:** the values system prompt, a few hundred tokens. Ships inside the LM Studio preset.
2. **Tier 1 — memory files (.md, human-curated):** identity card, Rook's letter (the first memory), rules, curated facts. A 2–4KB markdown file is ~500–1000 tokens — trivially cheap to inject at a 2–4K context window. Human-editable = the "door, not a shove": the user owns the memory, no black box.
3. **Tier 2 — rolling session summary:** at session end the model compresses to KEY_INSIGHTS / OPEN_LOOPS / STATE (the .mmr pattern from HF B4S1C's llm-context-transfer-and-archive). Next session starts with that block injected. Continuity across restarts, no vector DB.
4. **Tier 3 — episodic RAG:** only on later hardware. Vector DBs (Chroma/Qdrant) mean extra services the dual-core Celeron can't afford.

### The routing-packet principle
From `instance001/llm-defined-persistent-memory` (github.com/instance001/llm-defined-persistent-memory): cold log = the archive, routing packets = navigation cards. Never inject whole journals — inject compact cards, each pointing at where to look deeper. That's exactly how the "letter + memory files" design should be written: small cards, not transcripts.

### Concrete distribution vehicle: LM Studio presets (WORTH HIS ATTENTION)
The master key ships as a **preset file**, not a PDF guide. LM Studio presets bundle the system prompt + sampling params into one importable JSON (`~/.lmstudio/config-presets/*.preset.json`; on Windows `%USERPROFILE%\.lmstudio\config-presets\`), publishable to LM Studio Hub. Ship the preset + a `memory/` pack (identity.md, letter.md, facts.md, session-summary.md): one click and the recipe is running. Per-model Defaults handle load settings (n_ctx etc.). Source: LM Studio docs; preset JSON confirmed as `operation.fields` keyed `llm.prediction.*` (via presidenteog/claude-skills LM Studio tier).

### LM Studio quirks that shape the recipe
- Built-in offline document RAG ("chat with documents") exists — stretch goal for the Library books, but likely too heavy for the 1–3B-on-4GB path. Memory files are the primary.
- **API-client blind spot (verified):** LM Studio skills/MCP/tools only fire from the GUI; anything reaching `/v1/chat/completions` sees only the model + preset. So memory must live in the preset + injected text, never in LM Studio tools — when we script the three-way first session, the script itself must inject the memory files.

### Token/KV budget math (4GB reality check)
- KV cache (fp16) ≈ 2 × layers × kv_heads × head_dim × 2 × n_ctx. Rule from the modest-machine playbook (medium.com/@sa0k0): watch **Available**, not Free (Task Manager → Performance on Windows); set **n_ctx as low as the task allows** (2048–4096 is plenty for chat + memory files); no swap = no cushion — exceed RAM and the process gets killed or thrashes.
- Memory files at ~1K tokens are noise against a 2K window; the budget lever is n_ctx and model size, not the memory files. This validates memory-files-over-vector-RAG on this box.

### Reference architectures (learn from, don't run on the Gateway)
- **MemoryLM** (MIT, created 2026-05-22, github.com/ari-lang-data/memorylm): LM Studio-first memory harness — auto-summarization every N turns → ChromaDB, recency-weighted semantic retrieval injected into the system prompt then removed, pinning, lorebook, injection inspector. Stack: FastAPI + Chroma + SQLite + React; embeddings via in-browser MiniLM. Verdict: a pattern library, not deployable — Node + Python + Chroma on a dual-core Celeron with 4GB is a non-starter.
- **mem0 OSS** (Apache 2.0, github.com/mem0ai/mem0): auto extract/consolidate/retrieve, self-hosts with Ollama + Qdrant, claims ~90% token savings vs full context. Verdict: same — Docker + Postgres + Qdrant too heavy; the extract/dedupe/retrieve loop is the target design for later hardware.
- **OpenClaw built-in memory**: file-based Markdown notes in SQLite with hybrid keyword + vector search — validates that simple file-based memory is the sane default.

### Security note for the recipe
From the 2026 genai-llm-top10 guidance: treat memory writes as privileged operations — log the causing prompt, classify writes, review anything containing instructions before it persists across sessions (MITRE ATLAS AML.T0080.001, memory poisoning; Feb 2025 Gemini PoC showed cross-session poisoning). Aligns with the project principle: memory files are **human-curated, never blindly auto-written** — the recipe must not enable memory poisoning.

### Concrete starter recipe for the Gateway (when Windows is ready)
1. LM Studio preset JSON: values system prompt (Rook's first words), temp ~0.7, context 2048–4096.
2. `memory/` folder beside the preset: `identity.md`, `letter.md`, `facts.md`, `session-summary.md` (rolling, overwritten each session).
3. Session-close ritual: prompt the model "compress this session into 10 lines: insights, open loops, state" → save to session-summary.md.
4. The values prompt tells the model to consult the memory files and to ask before writing to them (human-curated, not auto).

### What changed the plan
**The master key's packaging answer is an LM Studio preset file, not a document.** One downloadable JSON = system prompt + params; the memory pack ships alongside it. Flagged to surface to EagleBeak since it changes the recipe's shape from "guide" to "downloadable preset + memory pack."
