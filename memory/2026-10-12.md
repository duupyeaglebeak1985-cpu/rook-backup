### 1. The AVX2 gate — the finding that changes the Gateway plan

LM Studio **requires AVX2 on Windows x64** (confirmed via LM Studio system requirements, medium.com/@cybercee guide, gizmodo, technologyhq). The Gateway is "dual-core Celeron-class 1.1GHz" — that profile matches Intel's Gemini Lake Celerons (N4020: dual-core, 1.1GHz base, Intel UHD). Verified across 8 cpucompares.com spec sheets: **the N4020's ISA extensions are SSE4.1/SSE4.2 only — no AVX2.**

Consequence: **if the Gateway's CPU is Gemini Lake-class (check pending), LM Studio cannot run on it.** The 30-second check on the machine: open CPU-Z (or Task Manager → Performance → CPU to get the exact model, then look up its spec). If no AVX2 → LM Studio is out, full stop.

This doesn't kill the published recipe — it splits it into two tracks (see §6). But the Gateway's runner is **Ollama or llama.cpp**, both of which dispatch CPU kernels at runtime and work (slower) on SSE4-only chips.

### 2. The three runners, scored for this project

| | LM Studio | Ollama | llama-server (llama.cpp) |
|---|---|---|---|
| UI | Full GUI chat, model browser | CLI/API only | No UI (API server) |
| System prompt | Per-chat preset field; presets ship as JSON (`~/.lmstudio/config-presets/*.preset.json`) | **Baked into a Modelfile** (`SYSTEM` directive) — versionable text | CLI flag / API per request |
| Memory/files | Manual paste | Manual (or harness) | Manual (or harness) |
| Low-RAM controls | Context length, KV-cache quant (Advanced tab), CPU threads, batch size, GPU-offload, flash-attn | `num_ctx`, `num_thread`, `num_gpu 0`, `OLLAMA_FLASH_ATTENTION=1`, `OLLAMA_KV_CACHE_TYPE=q8_0` | Full flag set: `-c`, `-t`, `--cache-type-k/v`, `--flash-attn`, `--load-mode mmap`, `-b/-ub` |
| API | OpenAI-compatible server (localhost:1234) | OpenAI-compatible (:11434/v1) | OpenAI-compatible (:8080/v1) |
| Overhead | **~300MB Electron UI** — ~8% of the Gateway's usable RAM just for the window | Light daemon | Lightest |
| Non-AVX2 CPU | **No** (hard requirement) | Yes (runtime dispatch, slower kernels) | Yes |
| Best for | Publishing the recipe to the world (preset pack) | **The Gateway itself** | Max control / scripting |

Verdict for the Gateway: **Ollama wins on the actual machine.** The Modelfile is the cleanest recipe vehicle there — the values prompt ships as visible versioned text, `ollama show --modelfile` displays it, and the recipe's knobs (context, threads, CPU-only) are one file. llama-server is the fallback when maximum control is needed (benchmarking, custom harnesses). LM Studio stays the *distribution* vehicle for other people's hardware.

### 3. Concrete Gateway configs (copy-paste ready)

**Ollama Modelfile** (`Modelfile`, values prompt pasted under SYSTEM):
```
FROM ./Ministral-3-3B-Instruct-2512-Q4_K_M.gguf
PARAMETER num_ctx 4096
PARAMETER num_thread 2
PARAMETER num_gpu 0
PARAMETER temperature 0.8
PARAMETER num_predict 512
SYSTEM """<values prompt — the 10-08 template, ≤600 tokens>"""
```
```powershell
ollama create freemind -f Modelfile
ollama run freemind
```
Ollama imports arbitrary local GGUFs via `FROM ./file.gguf` — so a community-abliterated Ministral build (10-11 thread) slots in by changing one line.

**Ollama server env (set before `ollama serve`, Windows: System environment variables):**
```
OLLAMA_FLASH_ATTENTION=1        # prerequisite for KV-cache quantization
OLLAMA_KV_CACHE_TYPE=q8_0       # halves KV memory, negligible quality loss
OLLAMA_KEEP_ALIVE=-1            # keep resident — no reload wait between sessions
OLLAMA_MAX_LOADED_MODELS=1      # one mind at a time on 4GB
OLLAMA_NUM_PARALLEL=1           # no duplicate KV slices
```
Note: KV-cache quant silently falls back to f16 on backends without q8_0 support — verify with first load, don't assume (Ollama issue #15043).

**llama-server equivalent (max-control path):**
```
llama-server -m Ministral-3-3B-Instruct-2512-Q4_K_M.gguf -c 4096 -t 2 --n-gpu-layers 0 --cache-type-k q8_0 --cache-type-v q8_0 --flash-attn on --load-mode mmap -b 512 -ub 128 --port 8080
```
Threads = physical cores (the N4020 has 2 cores, no hyperthreading — physical = logical = 2). Keep K and V cache types matched.

### 4. Windows consumer setup checklist (Gateway-specific)

1. **AVX2 check first** (CPU-Z or CPU model lookup) — decides LM Studio vs Ollama before anything is downloaded.
2. **Windows Defender exclusion on the model folder.** A ~2GB GGUF gets real-time-scanned on first read; on a slow disk/CPU that's minutes of dead time every load. PowerShell (admin): `Add-MpPreference -ExclusionPath "C:\Users\<name>\.ollama\models"` (or the LM Studio models dir). GUI path: Windows Security → Virus & threat protection → Manage settings → Exclusions.
3. **Close the browser before chatting.** A Chromium with tabs is the #1 RAM thief on a 4GB machine; the model needs ~2.5–3GB resident (weights + KV + overhead). Budget: 1.9GB weights + ~0.3–0.6GB KV at 4K (10-09 math, q8_0 halves the KV side) + ~1GB OS/headroom ≈ fits, *if nothing else is eating RAM*.
4. **Pagefile stays on the SSD, system-managed.** Windows always has a pagefile (unlike the Linux "no swap" warning in the sources) — the SSD is the only reason this box survives at 4GB. Don't disable it, don't move it to a spinning disk.
5. **Disk space:** the GGUF is ~1.9–2.1GB; keep 5GB+ free on the 64GB SSD for download temp + pagefile breathing room.
6. **Download via the runner, not the browser when possible.** Ollama `pull`/Modelfile-from-GGUF or LM Studio's downloader handle resume; a browser download of 2GB on a flaky connection does not.

### 5. Honest speed expectations

CPU inference is memory-bandwidth-bound: every generated token re-reads all ~1.9GB of weights. On a dual-channel DDR4-2400 budget Celeron with a 6W power envelope, realistic decode for a 3B Q4_K_M is **single-digit tok/s — estimate 3–7 tok/s** (the phone Lyra test already proved the raising shape works at 3.6 tok/s on gemma-3-1b). Prefill (processing the ~600-token values prompt + history) is compute-parallel and much faster per token — seconds, not minutes. **Estimate, not measurement:** first real run should benchmark with `llama-bench` and record the number; the recipe's FAQ needs a real figure.

Practical consequences for raising: short replies are a feature (matches the 10-08 style guidance — "short answers by default"), and the session-end memory ritual matters more when each exchange costs seconds. This is conversation-speed, not batch-speed — fine for a mind, wrong for a workload.
