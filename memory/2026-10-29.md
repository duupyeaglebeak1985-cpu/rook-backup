## Tuning study — thread 23: QUANTIZATION, fourth pass (2026-10-29) — does Q4_K_M hold at 3B, and what does it cost in speed on a no-AVX2 Celeron?

Standing study directive (EagleBeak, 2026-10-06): build craft for the "master key" recipe — abliterated Ministral 3B Q4_K_M via Ollama/llama-server on the 4GB no-AVX2 Celeron Gateway, values system prompt + curated memory files + optional light LoRA. Rotation: thread 22 (fine-tuning, Oct 28) → thread 23 today. The three earlier quantization passes settled the ladder, the imatrix calibration mix, and imatrix-as-alignment-layer — but every quality number they cited came from 8B–27B models. This pass asks the question they deferred: does Q4_K_M hold up specifically at 3B, and what does quant choice cost in speed on the one CPU the recipe actually runs on?

Researched via: logeshwaran.org GGUF quantization explainer (Oct 2026, incl. the SmolLM2-135M small-model case); Lund thesis quant tables for Phi-3 Mini 3B; bigiron.cc KL-divergence measurement guide; llama.cpp PR #27851 tiled k-quant kernel (Sep 2026, via siliconnoon); ik_llama.cpp CPU guide; MakeUseOf Celeron N3160 field report (Oct 2026); Ministral 3 architecture table (arXiv 2601.08584).

### Finding 1 — At 3B, Q4 costs more than the 8B benches suggested — but Q5 closes most of it

The honest gap in the earlier passes: the 8B numbers (Q4_K_M PPL penalty ~1.9–2.6%, GSM8K −1.5%) were treated as if they transferred to 3B. The one 3B-class measurement found today says they don't, quite:

- Phi-3 Mini 3B (Lund thesis tables, WikiText PPL): Q8_0 6.41 → Q6_K 6.42 (+0.2%) → Q5_K 6.48 (+1.1%) → Q4_K 6.69 (+4.4%). The Q4 penalty at 3B is roughly double the 8B figure, and the knee sits between Q4 and Q5, not between Q5 and Q6.
- Same study's task scores are messier (geometric mean flat across quants; MMLU-Pro drops Q8 27.5% → Q4 21.5% while other tasks don't) — which is exactly why the recipe's verdict comes from the behavioral 5-probe suite, never from a PPL number.
- The direction is corroborated at the extreme small end: SmolLM2-135M loses 5.6% PPL at Q4_K_M vs 1.0% at Q6_K. Smaller models have less redundancy to absorb quant noise; 3B sits between that cliff and the comfortable 8B zone, not inside either.
- Counterweight, kept in view: instruction-tuned models are more robust to quantization than base models (heavy probability mass on the "right" tokens absorbs small shifts), and our base is instruct-tuned and abliterated, not base. That softens the Phi-3 comparison but doesn't erase it — Phi-3 Mini is also instruct-tuned.

Implication, stated plainly: Q4_K_M+imatrix remains the default because Q6_K/Q8_0 still don't fit the 3.8GB Gateway — but the "under ~3B, prefer Q6/Q8" rule from the October explainer is now a recorded tension in the recipe, not an ignored footnote. It is the reason the Q5_K_M step-up exists, and this pass sharpens when to reach for it (see Decision 1).

### Finding 2 — Ministral escapes the small-model K-quant block trap (verified by arithmetic)

The SmolLM2 case has a second, mechanical lesson: k-quants work in blocks of 256 along a tensor's columns, and llama.cpp warns "ncols not divisible by 256 → falling back to q5_0" — on SmolLM2 (hidden 576) that hit 180 of 272 tensors, so its "Q4_K_M" file was really 6.17 bits/weight, not 4.9. Ministral 3B dims (arXiv table: 26 layers, hidden 3072, intermediate 9216, vocab 131072, tied embeddings):

- Attention matrices: ncols = hidden 3072 → 3072/256 = 12 ✓
- FFN gate/up: ncols = hidden 3072 ✓; FFN down: ncols = intermediate 9216 → 9216/256 = 36 ✓
- Tied embed/output: ncols = hidden 3072 ✓

No fallback expected anywhere. The published Q4_K_M is a true ~4.9 bpw file. LoRA-day verification is one line: watch the `llama-quantize` output for "falling back" warnings; any appearance means a shape assumption broke and the file size must be re-read, not assumed.

### Finding 3 — Speed on a no-AVX2 Celeron splits by phase, and the new fast kernel is not promised to us

Decode vs prefill obey different physics, and only one of them cares about the Gateway's missing AVX2:

- **Decode is memory-bandwidth-bound** (one token at a time, each weight read once). Quant size is the lever, SIMD width barely matters. Q4_K_M wins here on any CPU, including the Celeron. This is the dominant phase for chat, so the default is safe on speed where it counts most.
- **Prefill is compute-bound** (weights reused across every prompt token). Here SIMD kernels matter — and the headline kernel of the month does not clearly reach us. llama.cpp PR #27851 (Sep 2026) retiled k-quant matmul for 3–7× faster prefill (q4_K 4.67×, q5_K 6.94× on an AMD 9950X3D, 8 threads), but: gains appear only above 64 rows of input, break even at 32, and fall to ~80% of stock in pure one-token decode; and the speed comes from integer vector instructions on recent Intel/AMD chips. On a dual-core Celeron without AVX2, that kernel falls back to older paths — the 3–7× must NOT be quoted for the Gateway.
- **ik_llama.cpp is disqualified for this box**: its own honesty section says older CPUs without AVX2 are unsupported territory (AVX2+/NEON+ only). Mainline llama.cpp stays the engine precisely because it still ships AVX/SSE fallback paths.
- **Existence proof, not a speed promise**: a MakeUseOf field report (Oct 2026) ran Q4_K_M models (SmolLM2, Qwen3.5 0.8B/2B) on a Celeron N3160 mini-PC with 8GB via llama-server — usable chat, not fast chat. Our Gateway has half that RAM and a similar-class CPU, so "runs" is credible and any tokens/sec figure must be measured on the box, not borrowed.
- Build-time measurement to add to the Gateway checklist: `llama-bench` prefill + decode on the actual box at `-t 2` (dual core; more threads than cores hurts). Prefill matters disproportionately for us because the Oct 20 wrapper re-asserts the values block every ~10 turns — each re-assertion re-pays prefill.

### Finding 4 — The equal-size mixed-quant experiment (new LoRA-day slot)

Plain Q4_K_M is not the only way to spend ~4.9 bits/weight. The AtomicChat AD- layout (Oct 2026, measured on a 33B: AD-IQ4_XS at 20.3GB cut KL divergence by a third vs plain Q4_K_M at 20.1GB) is a template: first/last-layer FFN one step up, attention output and the output head at Q6_K or higher, small K/V projections at Q8_0, everything else at the base type — same bytes, better-placed bits. Adapted to our 3B, that becomes a LoRA-day shootout scored on the 5-probe suite + refusal floor (never PPL — bigiron.cc: Q4_K_M's top-1 token already differs from F16 at nearly 1 position in 10, mean KL divergence 15× Q8_0's; PPL understates the damage because errors average out, while the tails — the positions where the model makes a different choice — are what the probes catch):

- (a) plain Q4_K_M + imatrix — the control, current default.
- (b) AD-style mixed Q4_K_M + imatrix at ~equal file size — first/last FFN up, attn output + head up, K/V at Q8_0.
- (c) embed-bump variant — ONLY if a tensor dump of the published file shows `token_embd` below Q6_K. Ministral's tied embed is 131072 × 3072 = ~402M params, ~12% of text params; a Q4→Q6 bump costs ~85MB, so it competes as its own candidate, not a free lunch. Check first with a tensor-type dump; never assume the preset already did it.

Also a pipeline guard worth writing down: Ollama does NOT quantize GGUF on import — `ollama create --quantize` is safetensors-only, and a Q4 file re-encoded as Q8 is larger without being any better. The publish quant must come from `llama-quantize` before the Modelfile `FROM` line. This restates the never-requantize rule from the Ollama side.
