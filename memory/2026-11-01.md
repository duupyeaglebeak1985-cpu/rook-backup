### 1. Correction/confirmation: Ollama DOES have a no-AVX2 fallback — the Oct 12 verdict survives, stronger
- Ollama's own troubleshooting docs (docs.ollama.com/troubleshooting, checked 2026-11-01) state it ships multiple LLM libraries compiled for different CPU vector features and autodetects: `cpu_avx2` fastest, then `cpu_avx`, then plain `cpu` — "the slowest but most compatible." A 2026 Fedora CPU guide confirms the same in the wild: an older CPU gets "a Haswell or plain x64 build," visible in the log as `loaded CPU backend from .../libggml-cpu-*.so`.
- So the Gateway's SSE4-only Celeron should NOT hit an illegal-instruction wall under Ollama; it should land on the plain `cpu` backend and run slower. The old 0.3.x-era AVX-gate patch (forcing AVX on in source) is obsolete history, not something to repeat.
- Escape hatch if autodetection ever picks wrong: `OLLAMA_LLM_LIBRARY=cpu` forces the compatible library. Verify what actually loaded, don't assume:
  `sudo journalctl -u ollama --no-pager | grep -E "inference compute|loaded CPU backend"`
  Expect `library=cpu` and a non-haswell/non-icelake backend file. If the log ever reads `cuda`/`vulkan` on this box, something else was found — not expected here.
- What this does NOT change: LM Studio is still out on this CPU (AVX2 requirement stands from Oct 12). LM Studio stays the published-for-everyone-else track; Ollama is the Gateway track. Speed expectation on the plain backend, dual-core Celeron, 3B Q4: low single-digit tok/s is the honest planning number — usable for chat, not fast. Measure the real number with `ollama run freemind --verbose` (eval rate) at build time; don't quote a benchmark from a faster box.

### 2. Lubuntu install path, in order (after the OS itself is proven — OS-first gating from Oct 26 still stands)
1. `curl -fsSL https://ollama.com/install.sh | sh` — installs the systemd service, listening on 127.0.0.1:11434 by default. Good default: no auth on Ollama's port, so keep it loopback-only on this box.
2. Env vars go in a systemd DROP-IN, never by editing `/etc/systemd/system/ollama.service` directly — the installer rewrites that file on every update (Fedora guide, Oct 2026, Ollama 0.40.x):
   ```
   sudo mkdir -p /etc/systemd/system/ollama.service.d
   sudo tee /etc/systemd/system/ollama.service.d/override.conf << 'EOF'
   [Service]
   Environment="OLLAMA_MAX_LOADED_MODELS=1"
   Environment="OLLAMA_NUM_PARALLEL=1"
   Environment="OLLAMA_KEEP_ALIVE=-1"
   Environment="OLLAMA_FLASH_ATTENTION=1"
   Environment="OLLAMA_KV_CACHE_TYPE=q8_0"
   EOF
   sudo systemctl daemon-reload && sudo systemctl restart ollama
   ```
   (KEEP_ALIVE=-1 keeps the model resident — no reload wait between sessions. FLASH_ATTENTION is the prerequisite for KV-cache quantization; KV quant silently falls back to f16 on backends without q8_0 support, so verify on first load per the Oct 12 note — the plain `cpu` backend's q8_0 support is UNVERIFIED and must be checked at build time, not assumed.)
   Add `Environment="OLLAMA_LLM_LIBRARY=cpu"` to the same drop-in ONLY if the journal shows a wrong backend pick — don't pre-pin it and hide what autodetection would have chosen.
3. Model: `FROM ./Ministral-3-3B-Instruct-2512-Q4_K_M.gguf` Modelfile (abliterated build per the Oct 21/22 lineage) + SYSTEM values prompt + `PARAMETER num_ctx 4096`, `num_thread 2`, `num_gpu 0`; `ollama create freemind -f Modelfile`, then `ollama run freemind`.
4. Disk check first: the Ollama runtime alone is ~2.3 GB (it ships CUDA libraries even on a CPU-only box, per the Fedora guide), plus ~2 GB per 3B model. If internal disk is tight, relocate with `OLLAMA_MODELS=/path` — but NOT to the USB 2.0 stick as first choice: 10 MB/s read means a ~2 GB model load takes minutes even with mmap. Internal disk first, stick as backup/transport only.

### 3. llama-server fallback: build ON the box, never trust a prebuilt binary's ISA
- If Ollama ever fails on this CPU, the fallback is llama.cpp built from source ON the Gateway itself: with `GGML_NATIVE` defaulting to ON (`-march=native`), a build compiled on the Gateway can only emit instructions its own CPU has — SSE4.2, no AVX2 — so a native on-box build is inherently safe. The portable variant (for a binary built elsewhere) is explicit: `-DGGML_NATIVE=OFF -DGGML_AVX=OFF -DGGML_AVX2=OFF -DGGML_FMA=OFF` (the documented `noavx` flag set).
- Concrete build (needs `build-essential cmake git`, ~tens of minutes on a dual-core — run it in the background, not watched):
  ```
  sudo apt install -y build-essential cmake git
  git clone https://github.com/ggerganov/llama.cpp.git
  cd llama.cpp && cmake -B build && cmake --build build --config Release -j2
  ```
  Then the Oct 12 server line stands, with one addition — `--mlock` stays OFF on 4 GB (mlock pins RAM the box can't spare; mmap default lets the kernel page):
  `llama-server -m <gguf> -c 4096 -t 2 --n-gpu-layers 0 --cache-type-k q8_0 --cache-type-v q8_0 --flash-attn on -b 512 -ub 128 --port 8080`
- Do NOT download an upstream prebuilt release zip and assume it runs: prebuilt binaries target modern ISA unless the release says otherwise. Run it, watch for illegal instruction, and fall back to the on-box build. That check costs one command; skipping it costs a confusing crash.

### 4. RAM budget on Lubuntu — why the OS switch is what makes 4 GB work
- Lubuntu 24.04 LXQt idle is consistently reported at ~300–400 MB (up to ~800 MB with nothing active), vs Windows 11 eating most of the 4 GB before any model loads. That ~2 GB+ swing is the whole ballgame.
- Planning budget (estimates, to be verified with `free -h` at build time): OS ~0.4–0.8 GB + Q4_K_M 3B weights ~1.9 GB + q8_0 KV cache at ctx 4096 ~0.3 GB + runtime overhead ~0.2–0.5 GB ≈ 2.8–3.5 GB. Fits 4 GB, with no room for a browser with many tabs open alongside it. Rules that follow: one model loaded (MAX_LOADED_MODELS=1), ctx 4096 default with ctx 2048 as the first remedy if the OOM killer visits, and check swap before first load (`free -h`; `swapon -s`) — add a 2–4 GB swapfile if the install created none, as the safety net, not as working memory.
- The Oct 12 Windows-Defender-exclusion note dies with Windows; its Linux replacement is simpler: keep the model on internal disk (see §2.4) and don't run a desktop browser session at the same time as the first load test.
