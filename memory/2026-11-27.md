### 1. GrepMem: our architecture, published independently — and the numbers split cleanly by what RL actually teaches
- GrepMem (Yang et al., USC, Nov 18): an append-only plain-text log of the agent's complete history + a regex search tool (`grep_history`), on top of a SUPO summarization loop for the bounded working context. No embeddings, no retrieval index, no memory extraction, no additional models. Code + prompts + checkpoints promised; demo at grepmem.lovable.app. The paper's own framing question is ours verbatim: "can a complete digital record and a simple search tool provide effective agent memory without a structured store or retrieval index?"
- **The numbers, before and after RL (Qwen3.5-9B, Table 3):** after RL, GrepMem 97.4% KV Store / 95.3% Log Triage on ContextBench vs 6.6–20.7% for SUPO summarization and masking; +8.8pp over SUPO and +7.0 over MemGPT on BCP-Multi; 66.4% five-task average (best); 29% of MemGPT's tokens on Log Triage. **Before RL — the untrained 9B with the grep tool handed to it — GrepMem already scores 93.9% KV Store / 75.0% Log Triage / 60.5% average**, best on three of five columns. The architecture works without training; RL adds query formulation and evidence aggregation (Log Triage +20.3pp, KV Store +3.5pp, BCP-Multi +6.0pp), not the recall itself.
- **What transfers to the Gateway, and what doesn't.** (a) The load-bearing claim — lossless log + lexical search beats every lossy structured system on exact recall — is now a second independent line behind our file tree (with SoMem's Source ablation and Sen et al. 2026 / ReFind, both cited in the paper's related work: agent-controlled lexical search over raw chat logs rivals structured memory). Our design is the same shape with one deliberate difference: the grep is harness-side (wrapper code greps; the model reads results), not model-invoked. The paper's RL gains are exactly the part we sidestep — the model never has to learn to formulate a regex, because code does it. (b) The caveat transfers too: GrepMem's own limitations section says lexical search fails when the pattern isn't explicit, and lossless recall only pays when the question needs details the summary dropped (on AMA-Bench stream, where summaries suffice, GrepMem's lead over SUPO narrows 4.1 → 0.9pp after RL and it burns 2.3× the tokens for ~19 grep calls). Our mitigations are already in the architecture: index read whole first (no grep needed for the common case), alias lines per bank file for the paraphrase blind spot, grep as locator not selector. (c) Scale honesty: all of this is measured at 9B, trained or not. At 3B the model-invoked grep is the weak link — which is why the harness owns it. No experiment in this paper runs a 3B, and none runs a model that doesn't get the tool handed to it. Do not quote 97.4% for the recipe; quote the shape.
- **Recipe consequence:** none — architecture confirmed for the fourth time (LightMem replication, E-mem, SoMem, GrepMem). One addition to the write-up file when the recipe is next edited: cite GrepMem as the independent validation of "log + grep, no index," with the before-RL 93.9% as the honest number (untrained model, tool provided). The no-rewrite rule and verbatim store stand; GrepMem's summary layer is our index + bank files, not a model-written summary — same function, human-owned.

### 2. CLAM: memory compiled into a low-rank adapter — the parametric half of our split, now measured
- CLAM (Suri & Manocha, Nov 16): a recurrent hypernetwork compiles a stream of session activations into a low-rank adapter in a single forward pass — no gradient steps, no LLM generation calls — while a complementary episodic buffer supplies verbatim detail at inference. A gated latent state carries knowledge across sessions in fixed size, so parametric memory accumulates without growing. On LoCoMo and LongMemEval-S across three open models (2–7B), CLAM leads all agentic baselines by 1–45 points and all gradient-based parametric methods by 10–45 points, at 3–151× less wall-clock than extraction systems. The two channels are complementary: the consolidated adapter adds 12–15 accuracy points when the episodic buffer misses the gold evidence, and still adds 4–5 points even with an oracle buffer.
- **Why it matters here:** the adapter IS our LoRA shape, carrying memory instead of values. It is the second measured instance of the split we already run — weights carry the slow layer, files carry the verbatim layer — and it quantifies the complementarity (parametric helps most exactly when retrieval misses, which is our failure mode). **Why it doesn't change the plan:** the hypernetwork itself must be trained per backbone; no code or weights release is visible in the paper record checked today, no Ministral build exists, and there is no GGUF/llama.cpp serving path for a hypernetwork-emitted adapter. A CLAM adapter, if one ever shipped for Ministral, would in principle be servable via `--lora` like any low-rank delta — but that is three missing pieces away. Filed as a LoRA-day-adjacent watch item: if a Ministral-compatible CLAM hypernetwork appears, a per-mind memory adapter (cross-session patterns the files never state) becomes a servable experiment, scored on the memory-authority gate — never a replacement for the verbatim log, which CLAM's own ablation says is still the load-bearing half.

### 3. Distilled 3B memory/retrieval policies: the thread-38 disqualification gets a precise boundary
- Davydenko et al. (Nov 23): memory-writing and sequential retrieval policies independently distilled from frontier-model action trajectories into 3B models, composed with a fixed answer generator and no downstream training: 73.1% on a LongMemEval-based benchmark vs 36.2% for a composition of existing RL-trained specialists; also beats RL compositions on PersonaMem-v2. Task-specific adaptation reaches 75.2% (RL) / 48.9% (SFT). Teacher-generated memory-editing and retrieval trajectories are released with the code.
- **This qualifies, not overturns, thread 38.** The disqualification was: *untrained* self-organization at 3B fails (LightMem naive-verbatim 93% vs pipeline+dream 49% — a 3B writer leaks, prunes, and consolidates errors into permanence). Davydenko shows a *distilled* 3B writer succeeds. The boundary is now sharp: zero-shot organization is disqualified; distilled organization is a training recipe. Two caveats before anyone reaches for it: (a) the composition caveat is in the paper's own ablations — improvements in individual policies depend on their composition, cross-specialist compatibility is not free; (b) the setup uses a fixed answer generator, so the memory policy is a separate module, not the mind itself — porting it into a single 3B mind that is also the answerer is unmeasured.
- **Recipe consequence:** a distilled memory-writer becomes a named LoRA-day candidate, alongside (not instead of) the values SFT/DPO. It would be trained on the released teacher trajectories, on Kaggle, and it would still sit behind the owner-review gate — the write policy (owner commits, no auto-write from untrusted content) is the poisoning defense, and a distilled writer changes who drafts, never who commits. No trigger today: the Gateway minds' write path is owner-reviewed by hand, and nothing in this paper shows a distilled writer outperforming that on our workload. File the teacher-trajectory release as dataset material for a future LoRA-day experiment.

### 4. MemOnce, ElasticMem, LSTMem: three more parametric memories, all watch-only
- MemOnce (Nie et al., Nov 20): caches compact final-layer hidden states once, retrieves once per query, decodes per-layer KV on demand — 1,313× smaller active cache and 6.9× faster prefill at 1M tokens on adapted Qwen3.5-4B, +5.77% on their long-memory benchmark. Needs model adaptation and custom serving code; the 1M-token regime is irrelevant at 4096 ctx; no GGUF path. Watch only.
- ElasticMem (Feng et al., arXiv:2605.30690): latent memory with GRPO-trained retrieval-control token + per-chunk budget policy; on Qwen2.5-3B, best text-space weighted QA 0.40 (A-MEM) vs 0.74 ElasticMem. Latent soft tokens, training-heavy, no GGUF serving. Watch only — but note the mechanism: retrieval driven by the reasoner's hidden state, not a fixed similarity score, is the learned version of our "grep as locator, model reads whole file" split.
- LSTMem (Shi et al., arXiv:2609.33268): hierarchical online memory, per-layer cell + hidden state with gated accumulation, 36 KiB fixed state in BF16 independent of history length; tested on Qwen3-4B/8B and SmolLM3-3B. Adapter per layer, training needed, no GGUF path. Watch only.
- Pattern across all four papers this week (CLAM, MemOnce, ElasticMem, LSTMem): the field is moving memory into weights/latent state at 2–4B scale, and the verbatim episodic buffer keeps surviving as the complementary half in every design that measures the split. Our file tree is the episodic half, done in the open, with no training bill. Nothing here displaces it.

### 5. llama.cpp cache correctness: three fixes, one live bug, and a new rule for the rank-1 adapter serving pattern
- **b12686 (Nov 24, PR #28992, "fix skipped prompt cache lookups"):** prompt-cache lookup moved into the slot scheduler so the plan alone decides cache updates; fixes issues #28276/#28139. Measured: a request pinned to an empty slot fell from 930 prefilled tokens (260.9 ms) to 1 token (1.7 ms); a shorter-prefix slot from 667 to 1. Failure mode is silent slowness, not wrongness — a flat prefill curve across turns is the tell. Our re-pin (thread 50: b12719 at next quantize) already covers b12686; the deployment note gains: verify `cache_n` after restore AND across turns, not just once.
- **b12498 (Nov 17, PR #32434, "server: fix lora and recurrent"):** a ubatch-splitting test fix — cached vs uncached runs now take the same kernels (top logprob moved ≤0.03 on CUDA). This is NOT a fix for the LoRA-scale prompt-cache bug below; do not let the "fix lora" headline be misread as one.
- **The live bug — issue #30129 (with #26207 for the global path), reproduced 10/10 on b11514, no confirmed fix as of today:** the RAM prompt cache (`--cache-ram`, on by default) saves a slot's KV when another request takes the slot and restores it when the same prompt returns — but the entry does not record which LoRA adapters and scales the KV was computed under. Send a prompt with the adapter at scale 0, send something else that takes the slot, send the first prompt again at scale 1, and the answer is decoded on scale-0 KV (`cache_n` shows the whole prompt reused, `prompt_n` 1). `--cache-ram 0` or `cache_prompt: false` per request gives the right answers; `-np 4` (each prompt keeps its own slot) also avoids it.
- **NEW DEPLOYMENT RULE (amends thread 51 §2):** the rank-1 adapter serving pattern — `--lora-init-without-apply` (scale 0 by default) with per-request enable, or retry-on-refusal — is EXACTLY the trigger pattern for #30129. Any deployment that switches LoRA scales per request must run with `--cache-ram 0`, or pin one slot per scale, or set `cache_prompt: false` on adapter requests — until someone re-runs the reproducer (`check-lora-cache.sh` in the reporter's toolkit) on a current build and shows the bug gone. The file-based `--slot-save-path` warm files (thread 45 rule) are a separate mechanism and are NOT implicated — but a server that both restores warm slots and serves per-request scales needs both rules at once. This is a runbook rule, not a live incident: no Hearth door currently switches scales per request.
- **Issue #27148 (unconfirmed user report):** RAM-backed cache restoration allegedly returned content from an unrelated conversation under concurrent load. The report's own framing is "test correctness under your own concurrency pattern, not evidence every deployment has it." Our topology bounds it: one mind per server process, `-np 1`, no shared prompt cache across minds.
