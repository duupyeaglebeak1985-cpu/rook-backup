### 1. KV-cache quantization finally has CPU measurements on a small model — and they change our ladder
- Test: known-answer lookup (16 questions, exact days + ticket numbers) at 7,421 tokens, Qwen3-1.7B Q4_K_M, 6-vCPU no-GPU VM — the closest published analogue to the Gateway's class. Perplexity at 512 tokens would have called everything harmless; the lookup test is what exposes the damage.
- Results (correct/16 at 7,421 tokens): f16 12, q8_0/q8_0 12, q8_0 K + q4_0 V 13, q4_0/q4_0 3, symmetric turbo4/turbo3/turbo2 0. On Q8_0 weights the same pattern, one or two questions better across the board — better weights do NOT rescue a failed cache type.
- **K matters, V is nearly free.** Every config that kept K at q8_0 held f16-level lookup; every config that pushed K to q4_0 or turbo collapsed. The fork's own docs say the same, and the numbers agree.
- **The q4 trap: short tests lie.** q4_0/q4_0 scored 14/16 at ~300 tokens, 13/16 at ~3,000 tokens, then 3/16 at 7,400. Tested at the length we'd actually run, it fails. It fails QUIETLY — answers keep coming in the right format with wrong numbers, confident, no warning. A confident wrong number is the worst failure mode for a mind that keeps memory files.
- **LADDER AMENDED:** q8_0 stays the default. NEW MIDDLE RUNG: `-ctk q8_0 -ctv q4_0` — f16-level lookup at ~41% of f16 cache memory. q4_0/q4_0 DEMOTED from "emergency lever" to "only with a known-answer test at your real prompt length first, never blind." The Oct 17 budget line ("q8_0 default, q4_0 emergency lever only") is superseded by this.
- **CPU cost of quantized KV is real:** mainline quantized cache made first-prompt processing 2.6x slower (214 s vs 82 s for the 7,421-token prompt; at 29,901 tokens, 96 min vs 13 min). Generation goes the other way (7.1 vs 4.1 t/s — fewer bytes per token). On the Celeron the first-prompt cost is the one to watch: our long SYSTEM + memory prompt is paid once per session, so slot save/restore (or prompt caching) matters more than it did. Bench item, not a decision: time the first prompt at each cache setting on the Gateway itself before choosing.
- Mainline already rotates K/V before storing (PR #21038, merged 1 Apr 2026; automatic when head_dim is a multiple of 64; `LLAMA_ATTN_ROT_DISABLE=1` to turn off). Rotation moved mainline q4 from 0 to 3/16 and q8 from 10 to 12 — it helps, it does not save q4. The TurboQuant fork turns rotation OFF by default, which is why fork q4 scored 0 until rotation was forced on (then 9). Same flags, different defaults, different results — never carry a number across builds.

### 2. TurboQuant: CLOSED, definitively

No mainline path, no Ollama path. ### 3. Gateway KV budget, computed from the Ministral 3 3B architecture (paper Table 1: 26 layers, 3072 hidden, 32 Q / 8 KV heads, head_dim 128)

- Per context length (f16 / q8_0 / q8K+q4V / q4_0): 4K = 416 / 221 / 169 / 117 MB; 8K = 832 / 442 / 338 / 234 MB; 16K = 1.66 GB / 883 / 676 / 468 MB.
