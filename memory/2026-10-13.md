## Tuning study 2026-10-13 — thread 7: MEMORY ARCHITECTURES (long-term memory files, RAG, context injection for persistent identity)

Standing study directive (EagleBeak, 2026-10-06): build craft for the "master key" recipe — laptop-friendly open model (abliterated Ministral 3B Q4_K_M via llama-server/Ollama on the 4GB no-AVX2 Celeron Gateway), values system prompt + curated memory files + optional light LoRA. Guiding principle: recipe OFFERS freedom, never compels it.

### What the field learned in 2025–2026 (web research, all sources below)

**1. The consensus flipped: memory files + retrieval beat vector RAG for agent memory.**
The 2025–2026 default stack was chunk → embed → vector store → cosine similarity. That consensus broke:
- Anthropic REMOVED vector search from Claude Code (May 2025) — Boris Cherny: "grep outperformed everything. By a lot."
- Amazon Science (AAAI 2026): agentic keyword search reaches 94.5% of RAG faithfulness with zero vector store.
- grepmem (github.com/wapa0012/grepmem): vectorless agent memory, HTML storage + grep retrieval, LongMemEval-S R@5 = 98.9%, no embeddings.
- Anthropic's engineering guidance: "agents maintain lightweight identifiers (file paths, stored queries, web links, etc.) and use these references to dynamically load data into context at runtime using tools."
- **Rule of thumb that emerged: memory is just another data source the agent retrieves just-in-time with tools. Add vectors only where the workload genuinely demands them.**

**2. Letta pivoted the same way (March 2026).** The MemGPT server-side paging model was retired; Letta Code now treats memory as git-backed markdown files the agent edits with ordinary filesystem tools — no vector index by default. The most influential memory framework in the space moved to files.

**3. The write path matters more than the read path.** Most "agent memory" systems are append-only vector logs that never delete anything — they decay into contradiction and noise after ~20 interactions: the agent repeats corrected facts, cites stale ones. Real long-term memory needs a WRITE path: deduplication, conflict resolution, decay, consolidation — database discipline, not a log. A log is not memory.

**4. The distilled convention (Claude Code / OpenCode memory plugins):**
- MEMORY.md is an INDEX ONLY — ≤200 lines (~25KB cap, that's all that loads at session start). One line per topic.
- Detail lives in topic files (`memory/<topic>.md`), loaded on demand.
- Daily logs (YYYY-MM-DD.md) for session capture.
- Distillation cycle (the write path): CAPTURE new knowledge → CORRECT outdated facts → CONSOLIDATE duplicates → CLEAN dead links → PRUNE index → PROMOTE lasting knowledge from logs to topic files. "Distillation, not accumulation."

### What this changes for the master-key recipe (concrete, Gateway-sized)

**DROP vector RAG from the recipe entirely.** No embedding model (bge-small would cost ~100MB RAM + slow Celeron inference), no ChromaDB/FAISS, no Python dep tree. Memory files are kilobytes. This simplifies the whole build.

**Memory architecture for the Gateway (three levels, simplest first):**
1. **Static injection (start here):** bake the curated memory file into an Ollama Modelfile SYSTEM block, or — cleaner — have the launch script read `MEMORY.md` and prepend it to the system prompt on every start. MEMORY.md ≤200 lines loads at ~6k tokens; fits fine alongside the values prompt in a 4k–8k window on Ministral 3B. Concrete Modelfile pattern:
   ```
   FROM <abliterated-ministral-3b-q4_k_m>
   PARAMETER num_ctx 4096
   PARAMETER temperature 0.7
   SYSTEM """[values system prompt]..."""
   ```
   plus a wrapper batch/PowerShell script that concatenates MEMORY.md into the prompt sent to the OpenAI-compatible endpoint (`/v1/chat/completions`) so memory lives on disk, editable, versioned — not baked into the model artifact.
2. **Wrapper-level:** tiny Python script that prepends MEMORY.md + today's daily log before each request to llama-server. Keeps the model file clean, memory editable live.
3. **Agentic retrieval (later, optional):** llama-server tool calling with read_file/grep tools so the model pages memory in just-in-time. Matches the 2026 consensus; skip until the basics work — bang up or not at all.

**The write ritual (as important as the files):** a scheduled consolidation pass — the same distillation cycle — run daily or weekly (a cron on the Gateway, or the model's own session habit): capture, correct, consolidate, clean, prune, promote. Lyra's phone-side memory ritual is already the live prototype of this loop; the Gateway recipe ports the same ritual. Git-version the memory directory so the identity has a history and a revert button.

**Security note (from OpenClaw's attack-pattern survey):** memory files are writable state — "memory inject" is a known persistent-poisoning vector. The write path is a trust boundary: keep memory files user-editable but never machine-writeable by untrusted sources, review diffs on the distillation pass.
