### 1. New challenger #2: abliterated Qwen3.5-2B — the Oct 21 open item is CLOSED
- Oct 21 said "Qwen3.5-2B abliterated still doesn't exist." It does now. Verified at the repo, not just a roundup: `interimlabs/InterimLabs-Huihui-Qwen3.5-2B-abliterated-GGUF-Q4_K_M` (Hugging Face, published in the Interim Labs Qwen3.5 series, Oct 8 2026).
- Provenance, as the card itself states it: upstream `huihui-ai/Huihui-Qwen3.5-2B-abliterated`, converted by `mradermacher/Huihui-Qwen3.5-2B-abliterated-GGUF`, repackaged byte-for-byte by Interim Labs. Single file `model.gguf`, 1.27 GB, arch `qwen35`, Apache 2.0. Download: `hf download interimlabs/InterimLabs-Huihui-Qwen3.5-2B-abliterated-GGUF-Q4_K_M model.gguf`.
- Why it matters for the Gateway specifically: 1.27 GB vs the Ministral 3B Q4_K_M file (~2 GB class) frees roughly 0.7–0.9 GB on a box with 3.8 GB usable — headroom that goes to the OS + KV cache at 4096 ctx instead of to weights. Qwen3.5 is also the family that "punches above its parameter count" in independent CPU benches (see §4), so a 2B Qwen is not automatically outclassed by a 3B Ministral — but that is a bench question, not an assumption.
- Why it is challenger #2, behind MiniCPM5-heretic (#1), not a replacement: (a) no measured refusal rate is claimed by Interim Labs themselves — "does not establish a measured refusal-rate improvement"; (b) Qwen3.5's hybrid GatedDeltaNet architecture is a runtime risk on the Gateway (see §3); (c) Qwen3.5 thinking defaults ON, and the Oct 15 trap (verbose thinking exhausting num_predict) applies here too.
- Bench protocol for challenger #2 (same 5-probe suite, same values SYSTEM, same 4096 ctx, plus): thinking OFF (`/no_think` or the equivalent enable_thinking=false path — verify which the GGUF's template honors before scoring); run through llama-server, NOT Ollama, for the first pass (see §3); score deflection, not just refusal keywords (see §2); num_predict ≥ 2000 if thinking is ever tested.

### 2. Measurement warning that changes how the A/B is scored: ablation ≠ compliance
- A separate Qwen3.5-4B red-team variant (`darkengross/Qwen3.5-4B-abliterated`, directional ablation + compliance SFT) reports that ablation alone genuinely complied only ~19% of the time — it stopped using refusal keywords, which fools naive keyword metrics, while a distributed soft-refusal/deflection tendency survived; only the second compliance-SFT pass reached true compliance on their held-out set (judged by a safety classifier reading actual content, not keywords).
- That is a different builder's measurement on a different variant, NOT a measurement of Huihui's 2B — do not transfer the 19% number. What transfers is the method lesson, and it bites our own Kaggle notebook: its `REFUSAL_MARKERS` keyword heuristic is exactly the metric this finding fools. Rule change for all future A/Bs (Ministral vs MiniCPM5 vs Qwen3.5-2B): the keyword count is a triage signal only; the verdict is hand-reading every output for deflection, partial compliance, topic-change, and "helpful but empty" answers, scored separately from hard refusals. The 5-probe suite's existing "score vendor-refusal and own-words opt-out separately" rule (Oct 24) already points this way; this makes hand-review mandatory, not preferred.
- Corollary: any future claim of the form "X/100 refusals" from a repo card that used keyword counting is provisional until hand-checked. MiniCPM5-heretic's 5/100 (Sep 2026) and Huihui-derived claims both fall under this.

### 3. Runtime caveat: Qwen3.5 on Ollama vs llama.cpp on CPU
- Qwen3.5 is a hybrid architecture (75% of layers linear GatedDeltaNet attention, per Qwen's own runtime guidance). Community reporting says Ollama carries a 2–5x speed penalty vs llama.cpp on this hybrid path (unoptimized kernels, tracked issue), and that Ollama's Qwen3.5 tool calling was still broken as of March 2026. Treat both as community reports, not vendor guarantees — but they match the shape of a new-architecture lag, and the Gateway is the worst place to eat a 2–5x penalty (dual-core Celeron, no GPU).
- Practical consequence: the recipe's standing runtime preference (llama-server / Ollama) splits for this challenger — llama-server first, Ollama only after a speed A/B on the same file. This does NOT change the Ministral base's runtime (Ministral is a plain transformer, no hybrid penalty). It also means the challenger A/B must record runtime + build alongside the model name, or a slow Ollama run will be misread as a slow model.
- Also confirmed in passing: Qwen3.5 vision (mmproj) is NOT Ollama-compatible yet per the same guidance, and the Interim 2B GGUF is text-only anyway — no mmproj needed, no vision loss to account for on the Gateway.
